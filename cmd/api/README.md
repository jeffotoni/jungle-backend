# API

The API is the synchronous HTTP entry point of the project.

It receives authenticated requests, validates transport data and access, executes application use cases, and persists financial state in PostgreSQL. Quick is used at the HTTP edge, `github.com/jeffotoni/log` provides structured JSON logging, and Uber Fx composes dependencies and manages the process lifecycle.

The API does not publish directly to SQS. Events generated by successful financial operations are written to the transactional outbox in the same PostgreSQL transaction and are published later by the Publisher process.

## Request flow

### Write flow

```text
CLIENT
  |
  v
HTTP / Quick
  |
  v
HTTP middleware
  |
  +--> Trace ID and structured request logging
  |
  v
Handler
  |
  +--> Authentication and authorization
  +--> Route and payload validation
  +--> Idempotency-Key validation for wagering
  |
  v
Application / Domain
  |
  v
API repository
  |
  v
PostgreSQL transaction
  |
  +--> Check persistent idempotency and business deduplication
  +--> Lock the wallet when required
  +--> Validate business rules
  +--> Update wallet balance
  +--> Insert wagering transaction
  +--> Insert ledger entry when applicable
  +--> Insert transactional outbox event
  |
  v
COMMIT
  |
  v
HTTP response
```

Authentication, authorization and idempotency validation are currently performed at the handler boundary. The request logging middleware is provided by the HTTP server platform layer.

### Read flow

```text
CLIENT
  |
  v
HTTP / Quick
  |
  v
HTTP middleware
  |
  +--> Trace ID and structured request logging
  |
  v
Handler
  |
  +--> Authentication and authorization
  +--> Route parameter and query validation
  |
  v
Application / API repository
  |
  v
PostgreSQL
  |
  v
HTTP response
```

## Responsibilities

- Expose the official HTTP endpoints.
- Authenticate requests with OAuth2/OIDC against the configured identity provider.
- Enforce internal authorization and provider isolation.
- Validate request payloads, route parameters and query parameters.
- Require `Idempotency-Key` for `POST /wagering/transactions`.
- Execute wallet, wagering and reconciliation use cases.
- Persist financial changes through explicit PostgreSQL transactions.
- Protect wallet balances with database-level locking.
- Prevent repeated financial effects with persistent idempotency and business identity constraints.
- Maintain the append-only wallet ledger.
- Store domain events in the transactional outbox.
- Compare wallet balances with the ledger through reconciliation without changing the balance.
- Expose liveness and readiness endpoints.
- Produce structured JSON logs with request trace identifiers.

## Endpoints

- `POST /wallets`
- `GET /wallets/:walletId`
- `GET /wallets/:walletId/ledger?cursor=...&limit=50`
- `POST /wagering/transactions`
- `GET /wagering/transactions/:transactionId`
- `GET /providers/:providerId/wagering/transactions/:externalTransactionId`
- `POST /wallets/:walletId/reconciliation`
- `GET /health/live`
- `GET /health/ready`

All business endpoints require a bearer token. Internal wallet and reconciliation operations require the configured internal role. Wagering operations also require the authenticated provider to match `providerId`.

# Terminal 1: configure and start the API.

The API process must use the same OIDC values:

```bash
export HTTP_ADDR=:8080
export DATABASE_URL="postgres://jungle:jungle@localhost:5432/jungle?sslmode=disable"
export OIDC_ISSUER=http://localhost:8081/realms/jungle
export OIDC_AUDIENCE=jungle-api
export OIDC_INTERNAL_ROLE=wallet-internal
export LOG_LEVEL=DEBUG
go run ./cmd/api
```

The local Keycloak realm imports the `wallet-internal` and `provider-a` confidential clients from `keycloak/realm-jungle.json`. The imported client secrets are `INTERNAL_CLIENT_SECRET` and `PROVIDER_CLIENT_SECRET`.

# Terminal 2: configure the token request and obtain the tokens.

Install `jq` and execute this complete block in the second terminal. Shell exports are local to each terminal:

```bash
export API=http://localhost:8080
export OIDC_ISSUER=http://localhost:8081/realms/jungle
export OIDC_AUDIENCE=jungle-api
export KEYCLOAK_TOKEN_URL="$OIDC_ISSUER/protocol/openid-connect/token"
export INTERNAL_CLIENT_ID=wallet-internal
export INTERNAL_CLIENT_SECRET=INTERNAL_CLIENT_SECRET
export PROVIDER_CLIENT_ID=provider-a
export PROVIDER_CLIENT_SECRET=PROVIDER_CLIENT_SECRET

export INTERNAL_TOKEN="$(curl -fsS -X POST "$KEYCLOAK_TOKEN_URL" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "client_id=$INTERNAL_CLIENT_ID" \
  --data-urlencode "client_secret=$INTERNAL_CLIENT_SECRET" \
  | jq -r '.access_token')"

export PROVIDER_TOKEN="$(curl -fsS -X POST "$KEYCLOAK_TOKEN_URL" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "client_id=$PROVIDER_CLIENT_ID" \
  --data-urlencode "client_secret=$PROVIDER_CLIENT_SECRET" \
  | jq -r '.access_token')"
```

The internal token contains the `wallet-internal` role. The provider token has provider identity `provider-a`, so wagering requests must use `"providerId": "provider-a"`.

## POST examples

The examples below assume that the bearer tokens were issued by the configured OIDC provider and `WALLET_ID` refers to an existing wallet.

### Create a wallet

```bash
curl -X POST "$API/wallets" \
  -H "Authorization: Bearer $INTERNAL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "playerId": "player-001",
    "initialBalance": {
      "amount": "25.00",
      "currency": "BRL"
    }
  }'
```

Save the `id` returned by this request:

```bash
export WALLET_ID="516be6a5-8338-4560-a723-0fc1e6e6e801"
echo "$WALLET_ID"
```

When a different wallet is created, replace the value with the `id` returned by the API.

### Process a BET

```bash
curl -X POST "$API/wagering/transactions" \
  -H "Authorization: Bearer $PROVIDER_TOKEN" \
  -H "Idempotency-Key: bet-001" \
  -H "Content-Type: application/json" \
  -d '{
    "providerId": "provider-a",
    "externalTransactionId": "bet-ext-001",
    "walletId": "'$WALLET_ID'",
    "playerId": "player-001",
    "roundId": "round-001",
    "gameId": "game-001",
    "kind": "BET",
    "money": {
      "amount": "10.00",
      "currency": "BRL"
    }
  }'
```

### Process a WIN

```bash
curl -X POST "$API/wagering/transactions" \
  -H "Authorization: Bearer $PROVIDER_TOKEN" \
  -H "Idempotency-Key: win-001" \
  -H "Content-Type: application/json" \
  -d '{
    "providerId": "provider-a",
    "externalTransactionId": "win-ext-001",

    "playerId": "player-001",
    "roundId": "round-001",
    "gameId": "game-001",
    "kind": "WIN",
    "money": {
      "amount": "20.00",
      "currency": "BRL"
    }
  }'
```

### Process a LOSS

`LOSS` requires the amount `"0.00"` and does not change the balance or create a ledger entry.

```bash
curl -X POST "$API/wagering/transactions" \
  -H "Authorization: Bearer $PROVIDER_TOKEN" \
  -H "Idempotency-Key: loss-001" \
  -H "Content-Type: application/json" \
  -d '{
    "providerId": "provider-a",
    "externalTransactionId": "loss-ext-001",
    "walletId": "'$WALLET_ID'",
    "playerId": "player-001",
    "roundId": "round-001",
    "gameId": "game-001",
    "kind": "LOSS",
    "money": {
      "amount": "0.00",
      "currency": "BRL"
    }
  }'
```

### Process a REFUND

`REFUND` references the original processed BET and credits its full amount.

```bash
curl -X POST "$API/wagering/transactions" \
  -H "Authorization: Bearer $PROVIDER_TOKEN" \
  -H "Idempotency-Key: refund-001" \
  -H "Content-Type: application/json" \
  -d '{
    "providerId": "provider-a",
    "externalTransactionId": "refund-ext-001",
    "walletId": "'$WALLET_ID'",
    "playerId": "player-001",
    "roundId": "round-001",
    "gameId": "game-001",
    "kind": "REFUND",
    "money": {
      "amount": "10.00",
      "currency": "BRL"
    },
    "referenceExternalTransactionId": "bet-ext-001"
  }'
```

### Process a ROLLBACK

`ROLLBACK` applies the inverse effect of a processed BET, WIN or REFUND and requires its reference.

```bash
curl -X POST "$API/wagering/transactions" \
  -H "Authorization: Bearer $PROVIDER_TOKEN" \
  -H "Idempotency-Key: rollback-001" \
  -H "Content-Type: application/json" \
  -d '{
    "providerId": "provider-a",
    "externalTransactionId": "rollback-ext-001",
    "walletId": "'$WALLET_ID'",
    "playerId": "player-001",
    "roundId": "round-001",
    "gameId": "game-001",
    "kind": "ROLLBACK",
    "money": {
      "amount": "20.00",
      "currency": "BRL"
    },
    "referenceExternalTransactionId": "win-ext-001"
  }'
```

### Reconcile a wallet

```bash
curl -X POST "$API/wallets/$WALLET_ID/reconciliation" \
  -H "Authorization: Bearer $INTERNAL_TOKEN"
```

Repeating a wagering request with the same `Idempotency-Key` and the same canonical payload returns the original result. Reusing the key with a different payload is a conflict. A different key cannot reapply the same provider/external transaction identity.

## GET examples

### Get a wallet

```bash
curl -X GET "$API/wallets/$WALLET_ID" \
  -H "Authorization: Bearer $INTERNAL_TOKEN"
```

### Get wallet ledger

```bash
curl -X GET "$API/wallets/$WALLET_ID/ledger?limit=50" \
  -H "Authorization: Bearer $INTERNAL_TOKEN"
```

Use the `nextCursor` returned by the response for the next page:

```bash
curl -X GET "$API/wallets/$WALLET_ID/ledger?cursor=<next-cursor>&limit=50" \
  -H "Authorization: Bearer $INTERNAL_TOKEN"
```

### Get a wagering transaction

Set `TRANSACTION_ID` to the `transactionId` returned by a wagering request:

```bash
export TRANSACTION_ID="<transaction-id-from-response>"

curl -X GET "$API/wagering/transactions/$TRANSACTION_ID" \
  -H "Authorization: Bearer $PROVIDER_TOKEN"
```

### Get a transaction by provider and external ID

```bash
curl -X GET "$API/providers/provider-a/wagering/transactions/bet-ext-001" \
  -H "Authorization: Bearer $PROVIDER_TOKEN"
```

### Health checks

```bash
curl -X GET "$API/health/live"
curl -X GET "$API/health/ready"
```

## Persistence

The API may persist:

- Wallets and their versioned balances.
- Wagering transactions and their persistent idempotency data.
- Append-only ledger entries.
- Transactional outbox events.

All financial writes that belong to one operation are committed atomically. The API never publishes an event before that commit.

## Components

```text
cmd/api/auth/          OAuth2/OIDC verification and authorization data.
cmd/api/config/        API-specific environment configuration.
cmd/api/handlers/      HTTP handlers and route registration.
cmd/api/models/        HTTP-only request and response models.
cmd/api/repository/    API-specific PostgreSQL queries and persistence operations.

internal/application/  Use cases shared by API and asynchronous processes.
internal/contracts/    Payloads shared between HTTP and asynchronous processing.
internal/domain/       Money, wallet, wagering, ledger and business rules.
internal/repository/   Shared PostgreSQL infrastructure, including pool and transactions.
internal/platform/     Shared platform adapters, including the HTTP server lifecycle.
internal/fxmodules/    Uber Fx composition for the API process.
```

The Consumer and Publisher are independent processes. The Consumer will process SQS messages using the same application use cases as the API, while the Publisher will publish committed outbox events. They are not started by `cmd/api`.

## Local prerequisites

PostgreSQL, Keycloak and LocalStack/SQS are provided by the project Docker Compose. The Compose file imports the local `jungle` realm and its test clients when Keycloak starts.

Start the local infrastructure:

```bash
docker compose up -d
```

Apply the database migrations in order before using the financial endpoints:

```bash
docker compose exec -T postgres psql \
  -U jungle \
  -d jungle \
  < migrations/000001_init.up.sql

docker compose exec -T postgres psql \
  -U jungle \
  -d jungle \
  < migrations/000002_api_financial_guarantees.up.sql
```

Confirm that the required tables exist:

```bash
docker compose exec -T postgres psql \
  -U jungle \
  -d jungle \
  -c "\dt"
```

The following tables should appear:

- `wallets`
- `wager_transactions`
- `ledger_entries`
- `inbox_messages`
- `outbox_events`

The API configuration is provided through environment variables, including `HTTP_ADDR`, `DATABASE_URL`, `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_INTERNAL_ROLE`, `TRACE_ID` and `LOG_LEVEL`.
